# 实现与进度回写

先读 [接入协议](../../references/protocol.md)，读取任务上下文和所需设计；确认用户指定的代码仓库与任务对应，WorkHub 本身不会替你检出或执行代码。

1. 复用已有 `work_item`，按需要拆分可完成的事项。用 transition_record 从 todo 进入 doing；遇到实际阻塞时记录 blocked 与原因，不因需要等待测试就谎报完成。
2. 在用户授权的仓库实现需求，遵守该仓库的指令、开发流程和测试约定。Skill 不额外授权提交、推送、部署或修改其他仓库。
3. 将重要实现决策写回相关设计或实施事项，引用代码位置和真实提交信息。发现缺陷用 `issue`，severity 与 blocking 依据影响填写；已知对应测试用例时用 checkIds 关联。
4. 完成具体事项后再标记 work_item 为 done。任务整体不能仅凭实现结束就报告通过验收；Owner 最终验收和状态门槛由服务端执行。
5. 若用户要求验证，按 [质量证据规则](../../references/quality-evidence.md) 运行测试并回写；只做开发时交接受影响的需求/标准、用例与未验证部分。

存在未提交修改时，不把测试结果绑定成干净 HEAD 的已验证结果。按仓库授权流程取得准确可复现的 commit 后再提交绑定 SHA 的证据，或如实记录尚未形成可验收证据的限制。
