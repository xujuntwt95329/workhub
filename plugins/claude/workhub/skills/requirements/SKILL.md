# 需求与验收标准

先读 [接入协议](../../references/protocol.md)，用 `get_task_context` 获取任务边界、已采用原则和当前版本。

1. 按用户目标整理功能范围、边界和未决问题；能从现有上下文判断的事项直接推进，无法判断的关键决策写为 `question`。仅确实阻塞本期目标时标记 blocking。
2. 适合归类时复用或创建 `requirement_group`；需求用 `data.groupId` 关联同任务分组。分组有稳定 UUID，改名更新分组自身。
3. 创建/修改 `requirement`，正文记录行为与边界，priority 使用 must/should/could。为独立、可验证的条件分别创建 `criterion`，通过 requirementId 精确关联需求。
4. 标准描述输入/条件、动作与可观察结果；避免只写“功能正常”。不要把实现步骤当验收标准，也不要一次把多个无法独立判断的结果混成一条。
5. 使用 `request_review` 提交实际写入后的版本。需求和标准分别有版本；不要用自我批准替代 Owner 确认。

当前上下文排除了拒绝/删除需求；需要查历史范围时调用 list_records 并明确区分状态。不要复制被拒绝需求来绕过拒绝决定。拒绝、删除、恢复由 Owner 在平台操作；如果用户要求范围调整，说明建议及所涉编号。

修改已有需求会让旧测试证据和豁免失效。结束时列出新增/修改的编号、待决点、受影响标准及需要复验的用例；使用 WorkHub 记录作为主交付物。
